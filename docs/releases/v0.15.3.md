# v0.15.3 — Go 1.26.11, cheaper purges, an explicit pool size, and a new image location

This patch release is built with Go 1.26.11 for a `net/http` vulnerability, stops two retention purges from reading
the whole call log, makes the database pool size a setting, tightens two provider-credential refusals and sends a
held oversized audit envelope once. It has **two migrations** (`00066`, `00067`), both expand-only. **The image has a
new name:** `ghcr.io/bitop-dev/open-mcp-portal`. Read [Image location changed](#image-location-changed) and
[Rollout](#rollout) before upgrading.

## Image location changed

The GitHub repository moved from `ncecere/open-mcp-portal` to `bitop-dev/open-mcp-portal`, and the image moved with
it. v0.15.3 is the first release under the new name.

| Releases | Image | Signing identity (`--certificate-identity`) |
|---|---|---|
| v0.15.3 and later | `ghcr.io/bitop-dev/open-mcp-portal` | `https://github.com/bitop-dev/open-mcp-portal/.github/workflows/image.yml@refs/tags/<tag>` |
| v0.15.2 and earlier | `ghcr.io/ncecere/open-mcp-portal` | `https://github.com/ncecere/open-mcp-portal/.github/workflows/image.yml@refs/tags/<tag>` |

Older images remain at the old name with their signatures, SBOMs and provenance; nothing was moved or re-pushed. The
OIDC issuer is unchanged (`https://token.actions.githubusercontent.com`), and so are the omp binaries' asset names: they
are signed with the new identity from v0.15.3.

What to change:

- **Kustomize overlays.** The base's image name is the match key of an `images:` entry. Change the entry's `name:`
  to `ghcr.io/bitop-dev/open-mcp-portal`, with `newTag: v0.15.3` and the v0.15.3 digest. **An entry that still says
  `ghcr.io/ncecere/open-mcp-portal` matches nothing, without an error:** the pods would run the base's tag instead of
  your pinned digest. Check that `kustomize build <overlay> | grep image:` shows
  `ghcr.io/bitop-dev/open-mcp-portal@sha256:<digest>` for both portal containers (`migrate` and `portal`).
- **Anything else that names the image** (your own Helm values, Compose files, plain manifests, mirrors or pull-through
  caches): use the new repository.
- **Signature checks.** `cosign verify` commands and admission policies (Sigstore policy-controller, Kyverno) need the
  new certificate identity for v0.15.3 and later. A policy that trusts only the `ncecere` identity refuses v0.15.3;
  trust both while you may still roll back.
- **The `omp` GitHub Action** still installs and verifies v0.10.1 with the identity it was signed with; nothing to change.

The Go module path stays `github.com/ncecere/open-mcp-portal`, so `go get` and imports of `pkg/ompclient` are unchanged.

## Security

- **Go 1.26.11.** The binaries and the image are built with Go 1.26.11, which fixes GO-2026-6859 in `net/http`. The
  portal's code reaches the affected function (`govulncheck` reports it), so this applies to every installation.
  v0.15.2 and earlier were built with Go 1.26.10.
- **Dependency updates:** pgx 5.12.0, go-jose 4.1.9, goose 3.30.0, kin-openapi 0.153.0, oapi-codegen runtime 1.9.0,
  `golang.org/x/oauth2` 0.38.0, `golang.org/x/text` 0.44.0, the Node builder image, and the web build and test tools.

## Retention purges no longer read the whole call log (#106)

A call-metadata or captured-payload purge batch that found fewer rows than it asked for (the usual case once a
backlog is cleared) read every call or payload, on every retention pass: 0.4 to 1.4 s at 300,000 rows on a test
server, now under 1 ms. Each purge now also bounds its scan by the shortest retention period any row can have (the
platform period or the shortest team override), so the same rows are deleted, oldest first.

**Migration `00066`** restates `omp_purge_mcp_calls` with the same signature, owner, grants, `SECURITY DEFINER` and
settings (checked in the same statement, so a failed check leaves the old definition), and builds an index on
`mcp_call_payloads (occurred_at)` with `CREATE INDEX CONCURRENTLY`. It runs outside a transaction and is safe to rerun:
an interrupted, invalid index build is dropped and rebuilt.

## Database pool size (#107)

- **`DATABASE_MAX_CONNS`** sets the number of connections in each replica's serving pool: default `20`, from 4 to 1000;
  an invalid value stops startup. When it is unset, a `pool_max_conns` already in `DATABASE_URL` is kept; when it is set,
  it wins. The migration command keeps its own default.
- Before, the pool was pgx's default of max(4, number of CPUs). A provider token refresh holds a connection for as long
  as the identity provider takes to answer (up to 10 s), so a slow provider and a burst of refreshes could exhaust a
  small pool. Releasing the connection during the outbound refresh is still open (#107).

## Provider credential fixes (#107)

- **A failed read is not "provider disabled".** When the database read of a server's linked platform provider fails,
  the portal now returns an internal error. Before, gateway calls reported "the auth provider is turned off", and
  connecting reported a missing provider (or, in the connection picker, silently hid it).
- **A narrowed call never gets the stored, broader token.** A narrowed token refresh that answers with an empty
  access token is refused (`provider_unavailable`) and not cached. On a service connection, a narrowed call is never
  sent the connection's stored, un-narrowed token: a narrowed retry after the upstream server rejects the token is now
  refused instead. The same gap on the personal-credential path is not reachable from the gateway today and is
  tracked as #116.

## A held oversized audit envelope is sent once (#93)

Only for installations with audit webhook sinks enabled. A required full-profile sink that reaches an oversized row
holds there until an admin acknowledges it (unchanged). Before, the sender resent that row's envelope on every pass
until then; now it sends it once.

- A failed send is retried with the usual backoff. An acknowledgement ends the hold. A settings change (enable or
  disable, destination, secret, profile or required) sends the envelope once more, to the new configuration.
- **Admin › Audit stream** shows, next to the held sequence, whether and when the receiver was sent the envelope, or
  the last failure.
- While a sink is held after the envelope was sent, its **Last success** time stays at that send instead of advancing
  with every resend. An alert or dashboard that reads it as "the sink is alive" will see it age while the hold lasts;
  the held state and lag are the signals for a hold.
- Delivery stays in order and at least once; the retention hold and the acknowledgement are unchanged.

**Migration `00067`** adds a protected table, `omp_audit_ext.sink_holds` (the held sequence, the sink revision and the
latest delivery result), and restates three sink functions (`finish_attempt`, `acknowledge_oversized`, `update_sink`)
with the same signatures. There is **no new enable gate**: a v0.15.2 sender never reads the table and keeps resending
the held envelope as before, while its calls keep the record current.

## Rollout

- **Image.** Pull `ghcr.io/bitop-dev/open-mcp-portal:v0.15.3` by digest and change your overlay's `name:` as described
  [above](#image-location-changed).
- **PostgreSQL connections.** Each replica may now hold up to 20 serving connections (before: max(4, CPUs), so 4 on a
  small node). Size PostgreSQL `max_connections`, or your pooler, for replicas × pool size, plus one surge pod during a
  rolling update, plus the migration's connections and `doctor`, before you roll out. Set `DATABASE_MAX_CONNS` (or keep
  a `pool_max_conns` in `DATABASE_URL`) to stay at a smaller pool.
- **Migrations `00066` and `00067`** are expand-only: one concurrently built index, one new table and restated functions
  with unchanged signatures. `00066` runs outside a transaction (the index build does not block writes); `00067` is
  one short transaction. v0.15.2 replicas run unchanged against the new schema during the rollout, and rolling back
  to v0.15.2 after migrating needs nothing in the database: the index and the table stay (v0.15.2 never reads the table).
  To roll back with a v0.15.3 base, keep `name: ghcr.io/bitop-dev/open-mcp-portal` in the overlay and add
  `newName: ghcr.io/ncecere/open-mcp-portal` with the v0.15.2 tag and digest.
- **Nothing else to configure.** No API change, no change to audit streaming gates.
